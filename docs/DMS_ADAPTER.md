# The `dms` adapter (F2 design, 11 November 2026)

Status: **design only. No adapter code exists yet.** The owner cut the session to this note; a cheaper model builds the skeleton and the network slice from it. When code exists and disagrees with this file, the code wins: fix this file.

Inputs: docs/F2_BRIEF.md and the files it lists. Method names and parameters were read from DMS 2.1.0's own QML (`$XDG_RUNTIME_DIR/dms-shell/<hash>/Services/DMSService.qml`, `DMSNetworkService.qml`), as DMS_OBSERVED.md did. The owner's running DMS was never contacted.

## 0. Shape

```
adapters/dms/
  DmsAdapter.qml      HostAdapter root for the ZÆTHERION session. Owns one DmsLink.
  DmsLink.qml         The only file that touches the socket. Runs the effects of DmsLinkMachine.js.
  DmsLinkMachine.js   Pure step(state, event, now) → {state, effects} (§2). Tested under Node, one test per row.
  DmsFeed.qml         One per (domain, DMS service): capability + "wanted" (a lease expression). Holds the last snapshot.
  DmsNetwork.qml      NetworkDomain on DMS `network` (§4).
  DmsNetworkMap.js    Pure mapping, DMS network state → contract values (§4). Tested under Node against the fixture.
  qmldir              generated by tools/make_qmldirs.py
```

- **One root per session.** `DmsAdapter` is the single `HostAdapter` the view receives, as `SerpantinumAdapter` is today. `adapters/quickshell`, `adapters/hyprland` and `adapters/serpantinum_assets` are modules of domain implementations that this root instantiates (like `adapters/common` now). The folder must be `serpantinum_assets`: a hyphen is not a valid QML module name and `make_qmldirs.py` skips it.
- **Two processes, two instances.** The resident and the panel (Z12) each create their own `DmsAdapter`, with their own two connections and their own leases.
- Domain files derive from the contract type (`NetworkDomain { … }`), so shared behaviour is by composition: each holds a `DmsFeed`, never a base class.
- No `adapters/dms/core.py` was created. If the core needs a host profile for this session, F1 or the merge adds it.

## 1. Request/reply → contract

`DmsLink.call(method, params, done, timeoutMs)`:
- `done(result, error)` runs **exactly once**: with the result, or with an error string: DMS's own error, `"timeout"`, or `"offline"` (not ready at call time, or the connection dropped before the reply). It never throws. Events arriving while the machine is stepping are queued and drained after, so a callback may call `call()` again.
- Ids are integers from 1 per connection. Pending requests die with their connection, so a late reply can't be mismatched. A reply with an unknown id is ignored.
- Default timeout 10 s, one timer armed for the earliest deadline, running only while something is pending.
- **Commands are never queued or replayed.** A call made while not ready fails at once. After a reconnect the adapter re-reads state (snapshots); it does not resend intents. A Wi-Fi toggle replayed after an outage would be a surprise.
- **Outcomes reach the view only through properties**, which come from DMS's snapshots. No optimistic updates. A failed command leaves the property as it was; the failure is logged (`dms: <method> failed: <error>`), payloads are not.
- When a domain is unavailable its methods return without sending anything.

Toggle-only verbs (`network.wifi.toggle` answers `{enabled}`) use one pattern, in the domain file:
1. Remember the wanted value; one flip in flight at a time; the newest request wins.
2. Flip only if wanted ≠ current.
3. The answer's `enabled` is newer than the last snapshot: keep it as an override until the next snapshot arrives. This stops a double click from flipping twice.
4. If the answer isn't the wanted value (the snapshot was stale), flip once more, then give up.

## 2. The link: transition table

State: `phase` (down · connecting · greeting · ready · unsupported), `path`, `attempt`, `apiVersion`, `cliVersion`, `capabilities`, `untested`, `problem` ("" · no-socket · offline · too-old · protocol), `pending`, `feeds` (key → service, capability, wanted), `ev` (closed · opening · open · closing), `subscribed`, `cache` (service → last snapshot).

`needs` = sorted unique `service` of feeds with `wanted` and `capability ∈ capabilities`, and only in phase ready.
Backoff: 100, 200, 400, 800, 1600, then 2000 ms. It runs only while down.

| Row | In | Event | Out, effects |
|---|---|---|---|
| L1 | any | `path(p)`, p new and not empty | Close both sockets, fail pending `offline`, clear capabilities and cache. → connecting, attempt 0. `openRequest(p)` |
| L2 | any | `path("")` | As L1 but → down, problem `no-socket`, no timer |
| L3 | connecting | `requestUp` | → greeting. Timer: greeting deadline, 3 s |
| L4 | connecting | `requestDown` or socket error | → down, problem `offline`. Timer: backoff(attempt++) |
| L5 | down, path set | `tick` at the retry time | → connecting. `openRequest` |
| L6 | greeting | first line, `apiVersion` < 38 | → unsupported, problem `too-old`. Socket stays open (its EOF is the signal that this DMS left) |
| L7 | greeting | first line, `apiVersion` ≥ 38 | → ready, `untested = apiVersion > 38`, attempt 0. `settleSoon` |
| L8 | greeting | first line is not a greeting | → unsupported, problem `protocol` |
| L9 | greeting | `tick` past the deadline | `closeRequest`. → down, retry as L4 |
| L10 | greeting, ready, unsupported | `requestDown` | Fail pending `offline`, `closeEvents`, clear capabilities and cache, feeds get null. → down, retry as L4 |
| R1 | ready | `call` | Assign id and deadline, `sendRequest`, arm timer |
| R2 | not ready | `call` | `reply(error "offline")` |
| R3 | ready | line with a pending id | `reply(result or error)`, drop it |
| R4 | ready | line with an unknown id | Ignore |
| R5 | any | `tick`, a deadline passed | `reply(error "timeout")`, drop it |
| S1 | any | `feed(…)` or `unfeed(key)` | Update the table. `settleSoon` (the runner collapses a burst into one `settle` per event-loop turn) |
| S2 | ready, ev closed | `settle`, needs not empty | `openEvents`. → opening |
| S3 | opening | `eventsUp` | Send `{"id":1,"method":"subscribe","params":{"clientId":…,"services":needs}}`. subscribed = needs. → open |
| S4 | open | `settle`, needs ≠ subscribed | Drop cache of services no longer needed. `closeEvents`. → closing |
| S5 | closing | `eventsDown` | → closed. If ready and needs not empty: S2 |
| S6 | open or opening | `settle`, needs = subscribed | Nothing |
| S7 | open or opening | `eventsDown`, not asked for | → closed. Timer: backoff; on `tick`, S2 |
| S8 | open | event, service `server` | Update version and capabilities, re-run the L6/L7 gate, `settleSoon` |
| S9 | open | event, service ∈ subscribed | If it differs from the cached one: cache it, `state(service, data)` to the feeds |
| S10 | open | event with `error`, or an unsubscribed service | Log, ignore. No automatic redial |
| S11 | opening, closing | `settle` | Only note it; the list is compared again when the connection reaches open or closed |

Invariants, each with a test:
- **A subscribe is never sent without `services`** (DMS treats that as subscribe-all, which includes `clipboard`). Empty needs means no event connection at all.
- At most one event connection is open or opening.
- Every pending request is answered exactly once.
- No timer runs in phase ready with nothing pending.

## 3. Leases ↔ subscriptions

- DMS has no unsubscribe. Its own client changes the list by closing the event connection and dialling again; we do the same (S4, S5). Each new subscription starts with a `server` event and one snapshot per service, so nothing is missed: snapshots are whole states, not deltas.
- A `DmsFeed` is the only way to be subscribed. It registers on creation, updates when `wanted` changes, and unregisters on destruction. `wanted` is a lease expression: `wanted: root.holds("brightness")`.
- **The contract's un-leased properties need change events** (`network.connected` drives the island's glyph with no view lease, Z126). For those the feed is `wanted: true` for as long as the domain object exists. This is the only subscription without a view lease, and it is the minimum the existing contract allows. A deferred domain (`loadDeferred()`) holds nothing until it is created.
- `feed.data` is the last snapshot, or null while the feed is unwanted or unusable. Domain properties are bindings on it, so they fall back to contract defaults by themselves.
- A feed that becomes wanted for a service already subscribed gets the cached snapshot at once.
- Release takes effect at once (collapsed per event-loop turn). No linger: F3 can add one if measurements show churn.
- Leased one-shot work (a scan) is issued on the rising edge of `held && available`, so it is issued again after a reconnect.

## 4. Network (the slice to build first)

One feed, service `network`, capability `network`, `wanted: true`. `available = feed.usable && data !== null`, so nothing reads "disconnected" before the first snapshot.

| Contract | From the DMS `network` snapshot |
|---|---|
| `wifiEnabled` | `wifiEnabled === true` (override from the last toggle answer, §1) |
| `kind` | `"ethernet"` if `networkStatus` is ethernet and `ethernetConnected`; `"wifi"` if wifi and `wifiConnected`; otherwise by the flags, wired first; else `"none"` |
| `connected` | `kind !== "none"` |
| `name` | `wifiSSID` for wifi, `ethernetDevice` for ethernet (as Serpantinum does) |
| `ipAddress` | `wifiIP` or `ethernetIP` by kind, **only while `details` is held**, else `""`. No extra call |
| `networks` | Only while `scan` is held: `wifiNetworks`, skipping empty SSIDs, `outOfRange` and repeated SSIDs. `{id: ssid, ssid, strength: signal/100 clamped 0..1, secured, known: saved, connected}`. Replaced only when its content changes |

Decide `kind` from the boolean flags, never from whether a string is empty: the scrubbed fixture has placeholders in fields that were empty.

| Contract method | DMS |
|---|---|
| `setWifiEnabled(on)` | `network.wifi.toggle`, no params, answer `{enabled}`; the toggle pattern of §1. (`network.wifi.enable` exists but its meaning is unclear; no `disable` was seen) |
| `connect(id)`, saved network | `network.wifi.connect {ssid: id, interactive: false}`. Saved = in `savedWifiNetworks`, or in `wifiNetworks` with `saved`. Nothing if already connected to it |
| `connect(id)`, unknown network | No DMS call. `DmsNetwork` signals `unknownNetwork(id)`; the root calls `hostActions.open("wifi")` (Z95: passwords live in settings) |
| lease `scan` | `network.wifi.scan`, no params, once per rising edge of `held && available && wifiEnabled`, one in flight. Results arrive in snapshots |

`network.credentials` (password prompts) is not subscribed by this domain. The settings surface holds that feed when it exists.

Limits: the contract has no kind for cellular or VPN, so a cellular-only machine reads "none". The lease table in ADAPTER_CONTRACT.md says nothing holds `scan`; `view/rooms/Devices.qml` does, on its "nearby" page.

## 6. Capabilities and versions

- Capabilities are read from the greeting on every connect and from every `server` event. They can appear later; then the feed becomes usable and the list is redialled (DMS's own client does this).
- A feed is usable when the link is ready and its capability is present.

| Case | Domain | What the view has |
|---|---|---|
| DMS down | `available: false`, defaults, methods do nothing | OFFLINE on controls, greyed glyphs (Z11, Z123) |
| Capability missing | the same, for that domain only | OFFLINE for that control (DMS_BACKEND.md). No island expansion: nothing went down |
| `apiVersion` < 38 | every DMS-backed domain unavailable, `problem: "too-old"` | OFFLINE; Settings says DMS is too old |
| `apiVersion` > 38 | **works**, `untested: true` | Settings notes the version hasn't been checked |
| Up, no network | `available: true`, `connected: false` | Wi-Fi glyph crossed out (Z126) |

- **Owner's decision, 11 November 2026:** a DMS newer than the checked one keeps working with a note in Settings; an older one is switched off. Minimum and checked version are both 38 (2.1.0), two constants in `DmsLinkMachine.js`. Raise the checked version only with a fixture recorded on that version. Z9 should be amended to say this at the merge.
- `cliVersion` comes from the `server` event only; the greeting doesn't carry it.

## 7. DMS restarts (≤ 5 s)

- **The socket path is given, never guessed.** `DmsLink.socketPath` defaults to `DMS_SOCKET` (Z10) and may be bound by the shell entry. No globbing of the runtime folder: stale files and stray instances make it wrong (F1_RECON.md), and the supervisor is the one that knows which DMS is the session's.
- **Resident:** it is DMS's child and ends with it, so every DMS start is a fresh resident with a fresh `DMS_SOCKET`. Nothing to restore.
- **Panel:** it survives. Death is seen at once as EOF on the request socket, including after SIGKILL (L10). When the new path arrives (L1) it connects immediately; feeds and leases live in the domain objects, which outlived the outage, so S2/S3 dial the same list again and snapshots refill the properties. Held scans are issued again (§3).
- A server that returns on the same path is found by the backoff, within 2 s.
- Requests in flight at death get `offline`. Nothing is replayed.
- The adapter's own share of the 5 s is the time from "new path known" to "available again": a connect, a greeting, a subscribe and a snapshot. The rest of the budget is the supervisor's restart delay.

### Needs from F1
1. **The current DMS socket path for the panel:** in its environment at spawn, and on change while it runs (a core topic such as `dms: {state, socket, pid, since}`). This must also cover `dms restart` (Super+R), where the new `dms` is not the supervisor's child.
2. **Stop an orphaned resident** after HUP or KILL. Otherwise it sits OFFLINE beside the new one.
3. **The source for Z123's expansions.** The resident dies with DMS, so it cannot draw "DMS went down"; see OPEN F2-1.

## 8. Privacy

- Never subscribe-all (§2). `clipboard` may appear in a service list or a method name only in a DMS-backed clipboard domain, inside a `holds("history")` guard. A static test fails any other file in `adapters/dms` that names it. For this owner the clipboard domain is cliphist, so today nothing names it.
- The cache of a service is dropped when the service leaves the list and when the link drops.
- **Keeping DMS's clipboard history off:** at each ready, when the capability is present, the resident's `DmsAdapter` reads `clipboard.getConfig` and, if `disabled` isn't true, sends `clipboard.setConfig {"disabled": true}` and reads it again. Not to be built until `clipboard.getConfig` has a recorded fixture (OPEN F2-4).
- No new recorded data is needed for network. Replies to action calls in tests are synthetic, written in the test with obviously fake values, and labelled so.

## 9. What to build, and its tests

1. `tools/dms_replay.py`, additive, keeping `Replay(fixture, path)`: honour `services` on subscribe (always send `server` first); optional request log file (one JSON line per request, plus connection open and close); optional script: synthetic replies, methods never answered, events pushed to subscribers after a method.
2. `tests/test_dms_link_machine.py` (Node, strip `.pragma` lines as `tests/test_clip_kinds.py` does): one test per row of §2 and one per invariant.
3. `tests/test_dms_network_map.py` (Node): §4 against the fixture's `network.getState` reply and `network` event; expected values computed from the fixture, not typed in.
4. `tests/test_dms_contract.py` (static): each DMS domain file derives from its contract type and overrides every method with the same parameters; each lease in §5 is checked by `holds("…")`; only `DmsLink.qml` uses `Socket`; the clipboard rule of §8.
5. `tests/test_dms_adapter.py` (`qs` offscreen against the stand-in run as a subprocess):
   - **Contract:** properties equal §4's mapping; one toggle per real change, none for a repeat; an error or a timeout leaves properties unchanged; an unknown network sends nothing and opens `wifi`; nothing is sent while offline.
   - **Lease:** list is `["network"]` with no view lease; `details` and `scan` gate their properties; one scan per acquire; a test feed for `brightness` grows the list and shrinks it again on release and on destruction; with no feeds the event connection is closed.
   - **Restart:** SIGKILL the stand-in, expect OFFLINE with defaults and `offline` for the request in flight; start another on a new `dms-<pid>.sock`, hand over the path, expect availability, the same list and a fresh scan within 5 s. Also the same-path case.
6. `tools/dms_smoke.py`, reusing `prepare` and `run_view` from `tools/smoke.py`: all rooms with `FixtureAdapter { network: dms.network }`, `DMS_SOCKET` pointing at the stand-in. Expect no binding errors, `details` held on Devices and released after, and no action call in the stand-in's log.

Checked on this machine (Quickshell 0.3.2), so the builder need not rediscover it:
- A Unix socket path is limited to 108 bytes. Tests need a short private runtime folder (`tempfile` under `/tmp` works; deep folders fail with "AF_UNIX path too long", and `qs ipc` then can't find the instance either).
- `Socket`: a failed connect emits `error` only (2 no such file, 0 refused by a stale file), with no state change. A dead peer emits `error` 1, then `connectionStateChanged`. Treat an error while not connected as "down" and make that idempotent.
- After SIGKILL the socket file stays and refuses connections.
- `connected = false; connected = true` in one turn works. Changing `path` while the target state is connected dials at once, so set `connected = false` first. Don't close a socket inside its own parser callback (DMS's client defers it); run close effects through `Qt.callLater`.
- `qs ipc --pid <pid> call <target> <function>` reaches an offscreen harness in about 25 ms, with string arguments and a string return. Python can drive a harness step by step with it.
- Baseline here: `tools/smoke.py` passes in 2.5 s. `tests/test_qmldirs.py` already fails on `tests/fixtures/nested/{lock,pamcheck}/qmldir: missing` (from the S1 nested work, not from F2).

Never exercised against a real DMS, because tests must not actuate: `network.wifi.toggle`, `network.wifi.connect` and `network.wifi.scan`. Their shapes come from DMS's QML. Check each once with the owner present.
